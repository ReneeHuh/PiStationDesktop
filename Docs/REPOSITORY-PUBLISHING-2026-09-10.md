# Repository publishing and recovery

Protocol 57, working tree based on `f8a8204`. HOST-08 and HOST-09 now have connected GitLab and Azure publishing implementations. GitHub publication uses the same remote and push workflow. Live account acceptance remains DEL-07; no provider repository was created during verification.

## Using publication

Open **Settings → Source control → Publish selected project**. Choose GitHub, GitLab, or Azure DevOps and enter the destination. GitHub takes an owner and server; GitLab takes a user/group namespace (including nested groups) and server. Azure takes an explicit organization URL and project. An `organization.visualstudio.com` URL is normalized to `dev.azure.com/organization`. Azure project permissions determine repository visibility; publication does not change them. GitHub and GitLab offer private/public creation.

Publication creates the provider repository, configures its HTTPS remote, pushes the captured current-branch commit without force, and configures the local branch's upstream. It does not commit working files. An unrelated `origin`, including a separate push URL, is preserved: the workflow uses `origin-1`, `origin-2`, and so on. The result names the actual remote, branch, commit, and repository. An empty local repository finishes with its remote configured and an explicit “no commits” message.

When an alternate remote is added, PiStation's existing PR controls still inspect `origin`; publishing does not change their repository selection. The returned publication URL identifies the newly published repository.

Choose **Resume existing repository** after an interrupted publication or after adding the first commit to an empty repository. Resume performs a provider lookup and never sends a create request. It does not change repository visibility. Reusing an existing operation identity returns its durable result without executing again; starting resume is an explicit new operation. After a lost creation response, inspect the selected provider before resuming. The host does not retry creation automatically or delete a created repository to undo a later failure.

The host records the last confirmed step (repository ready, remote configured, or pushed). It rejects invalid destinations before calling tools, checks the returned repository against the requested host/namespace/project, and stops before pushing if Git rewrites the remote URL. Provider output containing credentials is not copied into publication status or receipts. A branch change during repository creation stops publication; the actual push uses the captured commit identity to prevent a later local commit from changing the content in flight. The host accepts one publication at a time. The form prevents repeated submission and suppresses results after switching to another project/environment.

## T3 comparison and provider contracts

The comparison used local T3 `0a590fa01af66ec135d2ebf2d5542b08a37dc275`, not an assertion about current upstream parity:

- [SourceControlRepositoryService](../../t3code/apps/server/src/sourceControl/SourceControlRepositoryService.ts) separates provider creation, remote configuration, and push; it reports `remote_added` when no commits exist. Its tests exercise conflicting remote names and empty repositories.
- [GitLabCli](../../t3code/apps/server/src/sourceControl/GitLabCli.ts) resolves the namespace and creates a project through `glab api`. PiStation additionally pins the requested hostname and checks namespace/repository identity. See the official [namespace lookup](https://docs.gitlab.com/api/namespaces/#retrieve-namespace-details), [project creation](https://docs.gitlab.com/api/projects/#create-a-project), and [glab API](https://docs.gitlab.com/cli/api/) contracts.
- [AzureDevOpsCli](../../t3code/apps/server/src/sourceControl/AzureDevOpsCli.ts) creates a repository with `az repos create` and leaves visibility to Azure's project permissions. PiStation names the organization/project explicitly, disables inferred defaults, and normalizes the two supported organization URL forms before checking destination identity. See [Azure repository commands](https://learn.microsoft.com/en-us/cli/azure/repos?view=azure-cli-latest#az-repos-create) and [organization URL forms](https://learn.microsoft.com/en-us/azure/devops/extend/develop/work-with-urls?view=azure-devops).
- GitHub creation uses an explicit host/owner/repository with `gh repo create`, followed by a read-only API lookup. The CLI's [create implementation](https://github.com/cli/cli/blob/trunk/pkg/cmd/repo/create/create.go) parses fully qualified repository names.

The implementation is in [the publishing service](../src/PiStation.Host/SourceControl/SourceControlHostingService.Publishing.cs), with [typed request/result fields](../src/PiStation.Protocol/Models/SourceControlHosting.cs) and [native provider controls](../src/PiStation.App/Views/ShellPage.Publishing.cs). Existing hosting receipts and operate-access authorization cover the new workflow on the owning host.
