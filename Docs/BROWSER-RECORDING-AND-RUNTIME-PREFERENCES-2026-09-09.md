## Recording and artifacts

The subsequent [recording performance fixes](BROWSER-RECORDING-PERFORMANCE-2026-09-11.md) improve pacing and decoding and replace the original estimated fresh-rate calculation with a count of source frames actually encoded. The measurements below retain the original implementation's evidence; sustained native rate acceptance remains open.

The Pi browser tool now accepts `recording_start` and `recording_stop` with stable `tabId` targeting. Recordings belong to one controller, thread, environment and tab. Repeated starts fail; an agent cannot stop a human recording. The human recording button can stop the current tab's recording. Changing viewed threads does not stop capture. Closing the tab, losing its controller or revoking interaction cancels an unfinished agent recording. Startup/callback cleanup checks the original capture identity so a previous recording cannot cancel or feed frames to its replacement. `status` reports recording and encoder-completion state.

The old 1–12 FPS PNG-file loop is replaced by a latest-JPEG-frame buffer feeding Windows MediaStreamSource/MediaTranscoder. Browser settings persist 30/60 FPS requests. Capture is bounded to two minutes, 1280 pixels per edge and 64 MiB, with measured duration, source frames, encoded samples and effective fresh-frame rate. Finishing the automatic limit stops the screencast; the owner can still call stop to save the completed video. These are requested rates, not a promise of sustained 30/60 FPS: retained native moving-page measurements were about 21 FPS for a 30 FPS request and 28 FPS for a 60 FPS request. WEB-09 remains Partial until sustained-rate/background/resource qualification is established.

Stop finalizes MP4 on the Windows client and transfers it in ordered 64 KiB chunks to the owning host. The agent receives a host-readable path, ID, MIME type, byte count, creation time and SHA-256. The host checks principal, connection, interact access, active stop request, offsets, header and bounds; it discards interrupted partial uploads and cleans crash leftovers on the next controller open. It retains ten completed files per thread where old files can be deleted. Save recordings needed for longer retention elsewhere. Recording stop has a separate 120-second deadline for finalization and transfer; ordinary requests retain 30 seconds, and heartbeat deadlines remain unchanged.

## Pi preferences

Runtime settings now expose long/provider-default cache retention, install telemetry, offline startup and version-check preferences. Inherit preserves raw launch configuration and Pi defaults. Explicit choices reject conflicting raw variables/arguments. Presence-based off flags are removed instead of set to `0`; telemetry's supported explicit off value is `0`. Pi offline startup also skips version checks, so contradictory dedicated choices are rejected. Offline does not prevent model requests or all networking; cache retention is provider-specific. Dedicated launch preferences require Pi 0.85.0 or later.

Host runtime saves use a configuration revision. Stale saves fail with a reload instruction, and Reload host runtime settings discards the stale editor snapshot. Preferences apply to new or restarted runtimes. Read-only remote users cannot configure the host.

Provider transport uses Pi's public SettingsManager API through the existing resource-management bridge. Auto, SSE, WebSocket and WebSocket cached are supported. The UI explicitly identifies the target as this host user's Pi settings, which also affect future terminal Pi sessions; trusted project overrides take precedence. Saving transport checks the observed global-settings revision and preserves unrelated settings. A resources refresh reports the transport setting observed at startup, saved user/project settings and the running environment's cache/telemetry/offline/version values. Startup transport is configuration evidence, not a claim about the provider's negotiated network connection. Existing agents need restart.

## Cookie import

Browser settings provide an explicit local source-profile selection and Copy cookies action for Firefox and compatible Helium. Discovery alone does not read cookie values. The source is revalidated at import, then opened read-only to create a consistent SQLite snapshot. The destination is a fresh profile whose WebView storage belongs to the current environment. Its profile record is published only after the cookies are written and settings are durably saved; cancellation/save failure attempts to clear the unpublished destination.

Firefox schema-dependent expiry and SameSite values are translated; containers/private/partitioned identities are skipped. Host-only cookies omit the domain argument, preserving their scope. Domain, path, Secure, HttpOnly, expiry and declared SameSite are carried through. Helium supports Windows DPAPI keys and compatible AES-GCM values, including newer host-hash validation; app-bound/unsupported or undecryptable records are skipped. Chrome and Edge import is not offered. Counts report skipped and imported records, and cookie values are excluded from logs, status text and ordinary RPC metadata. Some sites will still require sign-in.

Input bounds are 128 MiB per source database, 10,000 cookies and 16 MiB of cookie names/values. Source database or write failures do not modify the original browser profile. Live installed-browser/sign-in acceptance, native destination readback across restart, and broader availability/lock/partial-result qualification remain required; fixture tests are not real-account acceptance.

Implementation: [source reader/decryption](../src/PiStation.ClientRuntime/BrowserCookieImport.cs), [explicit desktop import](../src/PiStation.App/Views/Controls/BrowserSettingsPanel.Import.cs), [durable profile publication](../src/PiStation.App/ViewModels/BrowserSettingsStore.cs). Cookie writes use the documented optional domain, expiry and SameSite fields of [CDP Network.setCookie](https://chromedevtools.github.io/devtools-protocol/tot/Network/#method-setCookie).
